## 1. Что строим

Прототип системы, которая оценивает работу оператора в диалогах по настраиваемому чек-листу.

**Контур 1 — Оценка**
1. Редактор чек-листа: критерии, формулировки, вес, тип ответа (да/нет или шкала), доступность N/A, секции. Новый критерий применяется через UI, без кода.
2. Оценка диалога: загрузка транскрипта, выбор чек-листа, запуск. Языки RU / KZ / EN. Реплики `bot` и `system` — только контекст.
3. Результат: по каждому критерию — ответ, балл, вес, объяснение, **реплика-доказательство**. Если действие пропущено — какой участок проверен. Для N/A — причина. Итог + баллы секций + отдельный флаг грубой ошибки.

**Контур 2 — Работа с результатом**
4. Карточка: из списка → транскрипт + результат. Клик по доказательству ведёт к нужной реплике / моменту записи.
5. Апелляция: критерий + комментарий.
6. Решение проверяющего: подтвердить / изменить + причина → пересчёт итога. Видны исходная оценка, решение, финальный результат.

**Данные:** DEV — 65 диалогов (60 чатов + 5 звонков; 35 RU, 15 KZ, 15 EN). Получаем GET-запросом к API организаторов (URL в `.env`, в git не коммитим). Подробно — [docs/GUIDE.md](docs/GUIDE.md).

**Ревью и готовность к защите:** [docs/REVIEW.md](docs/REVIEW.md). Финал с 10 примерами — `tools/jury_kit.py` (выгрузка наших оценок и сравнение с жюри).

**Правила оценки:** [за что снижаем, за что нет](docs/SCORING_RULES.md) · [регламент общения оператора](docs/OPERATOR_GUIDE.md).

**Чек-лист** ([docs/CHECKLIST.md](docs/CHECKLIST.md), [`checklists/default.json`](checklists/default.json)): 7 критериев с весами 10/15/20/20/15/15/5 = 100 (два из них — шкалы 0–20 и 0–10 с фиксированными ступенями) + 8-й «Грубые ошибки» — флаг без баллов (оскорбление, платная услуга в обход компании, раскрытие конфиденциальной информации). N/A перераспределяет вес, итог округляется до 2 знаков. Контекст компании — [docs/COMPANY.md](docs/COMPANY.md).

## 2. Как нас оценивают → наши цели

| Что увидит жюри (5 минут) | Наша цель | Критерий готовности |
|---|---|---|
| 1 мин: интерфейс, выбранный диалог | Чистый быстрый UI | Список → карточка за 1 клик |
| 2 мин: оценка, обоснование, переход к реплике, N/A, итог | **Точность и доказуемость** | Каждое доказательство реально есть в транскрипте; N/A с причиной; итог сходится с формулой |
| 1 мин: апелляция → решение → новый итог | Сквозной сценарий | Исходный и финальный балл рядом |
| 1 мин: замена критерия, повторная оценка | Конфигурируемость | Новый критерий через UI → оценка контрольного набора без перезапуска |
| Час 23: контрольные транскрипты | Надёжный пакетный прогон | Весь набор оценён до выступления, ошибки повторяются автоматически |
| README, стоимость | Прозрачность | Модель + $ за одну оценку посчитаны по фактическим токенам |

Скрытые требования, о которых легко забыть:
- UI должен адаптироваться как **HTML-компонент Dynamics 365** → без фреймворков, компоненты изолированы, URL API настраивается.
- CORS у API организаторов → все запросы к нему только с backend.
- Исходные `timestamp` не трогаем (чат `MM:SS`, звонок ISO 8601).

## 3. Варианты решения

Ниже — развилки, по каждой выбран вариант (★). Менять — только договорившись всей командой.

### 3.1. Как вызывать LLM

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Один вызов на диалог, все критерии в одном JSON** | Дёшево, быстро, модель видит весь контекст | На длинных диалогах и 8+ критериях падает внимательность |
| B. Один вызов на критерий (параллельно) | Точнее, легко перепроверить один критерий после апелляции | ×8 стоимость и лимиты API на батче |
| ★ **C. Гибрид** | Лучшее соотношение | Чуть больше кода |

**★ C = A + детерминированные проверки + точечный B:**
1. Один вызов со всеми критериями, **structured output** (JSON-схема), `temperature=0`.
2. Транскрипт подаётся пронумерованным: `[12] operator 00:34 | текст` → модель возвращает `msg_index`, а не придумывает цитаты.
3. **Валидатор после LLM (без модели):** `msg_index` существует, цитата — подстрока реплики, доказательство — реплика оператора (если критерий про оператора), N/A только где `na_allowed`. Не прошло — повторный вызов только по этому критерию (B).
4. Измеримое считаем кодом, а не моделью: есть ли реплики оператора, кто начал диалог (бот/оператор), оборвался ли чат (подсказка для N/A у «Завершения» и «Консультации»). Время первой реакции, теги и вложения **в оценку не входят** (так сказано в чек-листе).
5. Пересчёт итога после апелляции — **без LLM**, чистая формула.

### 3.2. Модель

| Вариант | Комментарий |
|---|---|
| ★ Платный API, быстрая модель (Claude Haiku / GPT mini-класса) | Хорошо знает RU/EN, приемлемо KZ; ~¢0.1–1 за оценку — посчитать на DEV |
| Сильная модель (Claude Sonnet / GPT флагман) | Точнее на KZ и спорных критериях; включаем, если на «золотом наборе» быстрая модель ошибается |
| Локальная модель | Бесплатно, но слабый казахский и медленно на 65+ диалогах — не берём |

Провайдер переключается через `.env` (`LLM_PROVIDER`, `LLM_MODEL`), чтобы сравнить модели за 10 минут.

### 3.3. Хранение
★ **SQLite** (один файл, ноль настройки, транзакции для апелляций). JSON-файлы проще, но при параллельной пакетной оценке легко испортить данные. Postgres — лишняя инфраструктура для демо.

### 3.4. Frontend под Dynamics 365
| Вариант | Комментарий |
|---|---|
| Один HTML с глобальными скриптами | Быстро, но не встраивается по частям |
| ★ **Web Components** (`<cqa-dialog-card>`, `<cqa-checklist-editor>`…) на vanilla JS | Каждый экран — отдельный тег, API-URL через атрибут `api-base`, стили внутри компонента. Ровно то, что нужно для HTML web resource в D365 |

### 3.5. Аудио у звонков
`<audio>` с `audio_url`. Backend добавляет к каждой реплике звонка `offset_sec` (ISO-время минус время первой реплики). Клик по доказательству → `audio.currentTime = offset_sec`. Исходный timestamp сохраняется.

## 4. Что выделит нас (по приоритету)

1. **Валидация доказательств** — ни одной выдуманной цитаты. Самое сильное на демо.
2. **«Золотой набор»**: вручную разметить 10–15 DEV-диалогов (все 3 языка, оба канала), скрипт `scripts/eval_golden.py` выдаёт % совпадения по критериям. Промпты и модель меняем только по цифрам.
3. **Кэш оценок** по ключу `hash(dialog) + checklist_version` — повторный прогон бесплатный и мгновенный.
4. **Пакетный прогон** с прогресс-баром, параллельностью (4–8 запросов), ретраями — критично для часа 23.
5. Сводка: средний балл по языку / каналу / критерию, самые проваливаемые критерии.
6. Экспорт результатов в CSV; история версий чек-листа.

Пункты 5–6 — только после того, как весь сценарий демо работает end-to-end.

## 6. Риски

| Риск | Что делаем |
|---|---|
| Организаторы заменят критерий на контроле | Чек-лист целиком в данных (`checklists/default.json`), промпт строится из него, формула общая — новый критерий работает без кода. Репетируем замену в час 20–22 |
| Модель путает «Нет» и N/A, придумывает шаги шкалы | Правила «Нет vs N/A» из PDF в промпте, валидатор: N/A только где разрешён, шкала только из ступеней |
| API модели упал или лимит во время демо | Все результаты уже в SQLite; демо идёт по сохранённым оценкам |
| Контрольный набор пришёл, а батч падает | Репетиция на DEV в час 20–22; `scripts/run_control.sh <group_id>` одной командой |
| Конфликты при слиянии | Владение папками + контракт + маленькие PR |
| Плохое качество на KZ | Проверить на золотом наборе к часу 14; при необходимости сильная модель только для KZ |

## Запуск

```bash
cp .env.example .env            # вписать CQA_API_URL; оценщики — LLM_PROVIDERS (по умолчанию Claude → Codex по подписке)
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.main:app --port 8000
# открыть http://localhost:8000  → сразу откроется интерфейс
```
При первом запуске база `data/cqa.db` наполняется сама: чек-лист, диалоги из `data/DEV.json`
(если файла нет — забрать набор кнопкой/запросом `POST /api/datasets/DEV/import`) и готовые оценки из `dataset/DEV/evaluations/`.
Без моделей и затрат: `SCORING_MODE=mock`. Документация API: http://localhost:8000/docs.

Контрольный набор (час 23):
```bash
curl -X POST localhost:8000/api/datasets/<group_id>/import
curl -X POST localhost:8000/api/evaluations/batch -H 'Content-Type: application/json' -d '{"group_id": "<group_id>"}'
curl localhost:8000/api/jobs/<job_id>      # прогресс
```

**Модель и стоимость:** Claude через официальный SDK `anthropic`, один вызов на диалог (+ повтор только по критериям, не прошедшим проверку цитат).
Замер на DEV-диалогах (чаты RU/KZ/EN + звонки), с обоснованиями на трёх языках: один ответ Claude Haiku 5.5 ≈ **$0.004–0.006**,
оценка из 3 ответов ≈ **$0.012–0.018** и ~25–35 с на диалог. Claude Opus 5.5 — примерно в 25–30 раз дороже. Подробности — [docs/DATA.md](docs/DATA.md).

Отладка промпта из консоли: `python -m backend.scoring data/DEV.json --limit 5`.
**Несколько ответов и резерв.** Каждый диалог оценивается `LLM_SAMPLES` раз (по умолчанию 3), ответы сравниваются
по каждому критерию голосованием; если модели разошлись — критерий помечается «на проверку» (`needs_review`).
Кто оценивает — `LLM_PROVIDERS`: сначала Claude (локальный Claude Code по подписке, можно несколько аккаунтов),
**Codex подключается только если Claude не отвечает** (нет CLI, лимит, ошибка). Для демо и честной цены — `anthropic` по API-ключу.
Подписочные режимы (`claude_cli`, `codex_cli`) — для разработки на своей машине, не для бэкенда с внешними пользователями.

**Своя модель (позже).** Задел — папка [`llm/`](llm/README.md): план дообучения, экспорт обучающего набора из проверенных людьми оценок и провайдер `local` (OpenAI-совместимый сервер: Ollama / vLLM). На сайте она появится в выборе оценщика рядом с Claude и Codex.
